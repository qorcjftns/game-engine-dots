# 개발 순서와 완료 기준

## 작업 방향

GUI 에디터를 먼저 사용해 볼 수 있도록 작은 PR로 진행합니다.
첫 실용 목표는 **프로젝트 생성·열기 → PNG 스프라이트 배치 → 속성 수정 → 저장·재열기**입니다.
각 구현 PR은 필요한 코드·테스트·사용 설명을 함께 포함합니다.
아래 번호는 개발 순서이며 GitHub의 실제 PR 번호가 아닙니다.
기여·리뷰 절차는 [PR #1](https://github.com/qorcjftns/game-engine-dots/pull/1)의 범위를 따릅니다.

## 0. 기존 기반을 실제로 검증

현재 소스를 재빌드하고 포맷·Clippy·테스트·CLI 계약 검사를 확인합니다.
기존 미추적 Cargo.lock은 내용을 검토한 뒤 이 기반 PR에서 다룹니다.
macOS·Windows CI를 추가하되 실제 창 실행 여부와 빌드 성공을 구분합니다.
현재 도구·doctor·기존 CLI 바이너리 확인을 현재 소스 검증으로 해석하지 않습니다.

**완료 기준:** 현재 소스의 검사 결과와 lockfile 검토 근거, 두 OS의 CI 결과 기록.
실패가 있으면 원인과 최소 수정을 같은 기반 PR로 처리합니다.
GUI 화면·문서·명령 계약 설계는 이 작업과 병렬로 준비합니다.

## 1. GUI 셸을 먼저 실행

별도 engine-editor에 egui/eframe(wgpu)을 도입합니다.
초기에는 고정된 장면 목록·중앙 뷰포트·속성 패널과 프로젝트 미열림 상태를 표시합니다.
GUI는 OS의 DPI 배율을 따르고, 게임 콘텐츠에만 별도 논리 해상도를 적용합니다.
라이브러리 버전은 호환성 빌드 후 고정합니다. 기존 Macroquad 데모는 확장하지 않습니다.

**완료 기준:** macOS에서 실제 에디터 창과 패널 확인, Windows 빌드·실행의 확인 범위를 각각 기록.
리뷰에 실제 화면을 첨부합니다. 숫자 API나 가짜 편집 기능으로 채우지 않습니다.

## 2. 프로젝트 문서·편집 명령·저장/열기

사람이 읽고 수정하기 쉬운 최소 JSON 문서에 `schema_version`, 안정된 개체 ID, 상대 리소스 경로를 둡니다.
구체적인 파일·명령 스키마는 이 구현 PR에서 확정합니다.
공통 편집 명령의 입력·검증·결과와 되돌릴 변경 정보를 이 단계부터 설계합니다.
선택·패널 상태를 문서와 분리하고, GUI에서 빈 프로젝트를 생성·저장·열게 합니다.
열린 문서는 GUI 편집 세션이 소유하고, 통신 구현 전 CLI·MCP의 동시 파일 덮어쓰기는 지원하지 않습니다.
원자적 저장과 오류 시 기존 파일·열린 문서 보존을 구현합니다.

**완료 기준:** 새 프로젝트를 저장하고 앱을 종료·재열기해 설정과 빈 장면 유지.
깨진 파일·저장 실패에도 기존 파일과 열린 문서가 손상되지 않는 검사 통과.
이후 GUI 편집이 사용할 명령 계약을 확정하고, 이전 값·삭제 개체·삽입 순서를 보존합니다.
최소 명령의 정·역적용으로 원문서를 복원하고, 명령 실패 시 문서·이력을 보존하는 검사 통과.

## 3. PNG 가져오기와 스프라이트 배치

PNG를 프로젝트 리소스로 가져오고 공통 명령으로 스프라이트 개체를 추가합니다.
장면 목록과 픽셀 뷰포트에 표시하며 GPU 리소스와 저장 문서를 분리합니다.
아직 전체 에셋 파이프라인이나 애니메이션을 만들지 않습니다.

**완료 기준:** PNG 추가 → 장면 표시 → 저장 → 재열기 후 이미지·개체 ID·위치 유지.
불러올 수 없는 이미지와 누락 리소스의 원인 표시. nearest 확대 실제 화면 확인.

## 4. 선택·속성 수정·드래그

장면 목록·화면 선택을 연결하고 속성 패널에서 이름·위치를 수정합니다.
뷰포트 좌표를 논리 픽셀로 변환해 끌어 배치하고 스냅합니다.
모든 문서 수정은 2단계의 명령을 거치며 드래그 한 번을 변경 한 건으로 기록합니다.

**완료 기준:** GUI만으로 프로젝트 생성 → PNG 배치 → 선택·위치 수정 → 저장 → 앱 종료 → 재열기 수행.
뷰포트 배율·여백을 바꿔도 클릭과 드래그의 대상·위치가 일치함.
이 단계가 첫 실용 편집 흐름입니다.

## 5. 실행 취소·다시 실행과 미저장 보호

기존 명령의 되돌릴 정보를 이용해 추가·속성 수정·드래그의 undo/redo를 연결합니다.
수정 표시와 저장·취소·변경 버리기 흐름을 제공하고 프로젝트 전환·종료 시 보호합니다.

**완료 기준:** 드래그 한 번의 undo/redo, 저장 후 수정 여부, undo 뒤 새 편집의 redo 이력 정리,
저장 실패·종료 취소 시 현재 작업 보존을 확인. Mac·Windows 실제 입력·종료 동작을 따로 기록.

## 의존성과 역할

| 작업 | 주 담당 | 병렬 가능 범위 | 먼저 필요한 결정 |
| --- | --- | --- | --- |
| 기반 검증·CI | 기반·검증 담당 | GUI 화면/계약 설계와 병렬 | 기존 실패와 확인 범위 |
| GUI 셸 | GUI 담당 | 검증 담당의 OS 점검 | GUI 라이브러리·패널·뷰포트 경계 |
| 문서·명령·IO | 코어 담당 | 계약 확정 후 GUI 메뉴와 IO 구현 병렬 | 스키마·ID·명령·저장 실패 정책 |
| 리소스·스프라이트 | 리소스·렌더링 담당 | 공통 추가 명령 구현과 GUI 연결 병렬 | 문서와 상대 경로 계약 |
| 선택·속성·드래그 | GUI 담당 | 명령 검증·좌표 변환 검사 | 개체 ID·편집 명령·드래그 묶음 |
| undo/redo·보호 | 편집 세션 담당 | 시나리오 검증 | 되돌릴 변경 정보·수정 상태 정책 |

총괄은 계획·범위·작업 배분·리뷰만 수행하고 모든 수정을 서브에이전트에 위임합니다.
공용 API를 먼저 정하고 한 파일의 작성자는 한 명으로 둡니다.
코드가 필요한 후속 PR은 선행 변경을 기준으로 진행하며, 관계없는 변경은 함께 넣지 않습니다.

## 첫 편집 흐름 이후

CLI 프로젝트 검사·장면 조회·공통 편집 명령 → MCP stdio 어댑터 → 실행 중인 편집 세션 공유 순으로 진행합니다.
동시 수정은 세션 ID와 문서 버전으로 충돌을 검출합니다.
그다음 타일맵·애니메이션·충돌·플레이 미리보기 등을 작은 편집 기능 단위로 추가합니다.
플레이는 편집 문서 복사본에서 실행하고 원본을 보존합니다.
배포 실행 파일·패키징·서명은 에디터 편집 기능과 별도 완료 기준으로 관리합니다.
