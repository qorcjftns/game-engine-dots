# GUI 에디터·공동 세션·runtime의 경계

제품의 전체 범위·순서·완료 판정은 [개발계획](roadmap.md)을 기준으로 합니다.
이 문서는 구현이 늘어나도 유지할 데이터·실행·플랫폼 경계를 설명합니다.

## 현재 기반과 미구현 영역

M1의 프로젝트 문서·GUI 편집 기반에 M2의 공동 세션 구현을 추가했습니다.
M2의 PR 병합 상태와 OS별 실제 검증은 [검증 기록](verification.md)을 따릅니다.
Rust, [egui](https://github.com/emilk/egui)/[eframe](https://docs.rs/eframe/latest/eframe/) 0.37.0,
[wgpu](https://wgpu.rs/)로 GUI를 구성하며 문서와 프로토콜 타입은 GUI 라이브러리에 의존하지 않습니다.

| 크레이트 | 현재 책임 |
| --- | --- |
| `engine-core` | 외부 의존성 없는 화면 배치·시간 규칙 |
| `engine-document` | 프로젝트 문서·PNG·편집 명령·IO·undo/redo |
| `engine-protocol` | disk/live 조회·변경 요청·receipt·오류의 공통 JSON 계약 |
| `engine-control` | 게시 snapshot·로컬 인증 TCP·변경 큐·원장·공통 client |
| `engine-editor` | 문서 단독 소유·GUI 입력·리소스 표시·logic에서 변경 적용 |
| `engine-cli` | 기존 info/viewport·저장 문서 조회·live 조회/변경/결과 확인 |
| `engine-mcp` | 공식 rmcp stdio 도구 3개에서 control client 직접 호출 |
| `engine-desktop` | Macroquad 출력 검증 데모 |

M3에서 `engine-runtime`이 문서·PNG 사본/입력/tick/논리 출력을, `engine-host`가 공통 egui 입력·표시를,
`engine-player`가 편집 UI 없는 창 수명을 담당합니다. 행동 코드·도트/대화형 에셋 제작·export는 아직 구현 전입니다.
기존 데모 실행을 프로젝트를 읽는 독립 player의 완성 근거로 사용하지 않습니다.
새 크레이트와 라이브러리는 실제 경계·실험 결과가 정해질 때 추가합니다.

## 서로 다른 네 상태

| 영역 | 소유하는 자료 | 보존 원칙 |
| --- | --- | --- |
| 프로젝트 문서 | 형식 버전·장면·안정 ID·자산 참조·편집 속성 | 사람이 읽는 JSON, 상대 경로, 검증 후 교체 |
| 편집 세션 | 열린 문서·저장 지점·undo/redo·revision·요청 결과 | GUI가 단일 소유, 실패 시 문서/이력 보존 |
| GUI 상태 | 선택·입력 draft·드래그 preview·패널·줌팬 | 문서와 분리, 한 조작을 한 명령으로 확정 |
| runtime world | 시작 snapshot의 개체/자산·실행 변수·tick·입력·접촉 | 편집 원본과 별개, stop 시 원본에 자동 반영하지 않음 |

```text
GUI / CLI / MCP → 편집 세션 → 프로젝트 문서
                                   ↓ 시작 snapshot
                         runtime world → 논리 픽셀 화면
                              ↑               ↓
                    입력 / 행동 / 충돌   Editor Play / 독립 player
```

M2의 외부 변경도 같은 명령·이력·저장 서비스를 사용합니다.
M3에서 editor와 독립 player의 실행·렌더 경계를 공유하고, 편집 서버를 player의 필수 의존성으로 만들지 않습니다.
실행 중 편집 변경은 초기에는 거부하며, 실행을 멈춘 뒤 편집을 재개합니다.

## 공동 편집의 단일 소유

실행 중인 GUI 한 개/프로젝트 한 개에 CLI·MCP를 연결합니다.
외부 프로세스가 JSON을 직접 덮어쓰는 방식으로 동기화하지 않습니다.
직렬 명령 처리·단조 revision·새 session ID·request ID 재조회 규칙은 [접근 규약](agent-interface.md)을 따릅니다.
TCP worker는 GUI가 게시한 확정 snapshot을 조회하고, 변경 큐는 GUI logic에서 검증·실행합니다.
CLI와 MCP는 같은 control client·원장을 사용하며 자체 문서·이력·저장 경로를 만들지 않습니다.

입력 draft·드래그·대화상자 중에는 확정 문서를 조회할 수 있지만 외부 변경·undo/redo·저장은 거부합니다.
요청 처리를 화면 그리기에만 묶지 않아 최소화·가려짐 중에도 기한과 결과를 관리합니다.
새 편집 기능의 GUI와 에이전트 어댑터가 서로 다른 규칙을 구현하지 않습니다.

## 픽셀·시간·입력

GUI 패널과 글자는 OS DPI를 따릅니다. 게임 장면·게임 텍스트/HUD·효과는 논리 픽셀 화면에 합성하고 nearest로 표시합니다.
에디터 UI의 OS system_fonts 사용과 게임 HUD의 배포 폰트는 별개입니다.
게임 폰트는 프로젝트/패키지의 리소스로 정하고 받는 기기의 OS 글꼴에 의존한다고 가정하지 않습니다.
기본 논리 해상도는 320×180이며 M1은 프로젝트별 가로·세로 1~4096을 지원합니다.
편집 뷰의 줌팬과 runtime camera를 구분하고 선택·드래그·타일 좌표는 검증한 변환을 공유합니다.

현재 60틱 계산은 실행 기반으로 재사용 여부를 검증합니다.
실시간 프레임 지연의 따라잡기 정책과 명시적 N tick 실행은 별도이며, 정확한 tick 요청을 임의로 생략하지 않습니다.
게임 입력은 action으로 변환하고 TextEdit·대화상자·focus 상실이 게임 조작으로 새지 않게 합니다.
성능은 실제 기기·부하 장면으로 측정하며 physics의 OS 간 비트 단위 동일성을 전제하지 않습니다.

## 행동 코드와 충돌 확장

v1에는 사용자가 엔진 소스를 수정하지 않고 행동을 작성하는 경로 하나가 필요합니다.
M3/4 실험에서 작성/검증 방법·실행 호스트·허용 API·중단·메모리/시간 예산·오류 위치·export 호환성을 선택합니다.
특정 언어, full IDE, 핫리로드를 먼저 확정하지 않습니다.
행동 오류·무한 루프가 editor를 멈추거나 편집 원본을 손상시키면 선택 실험을 통과한 것으로 보지 않습니다.
프로젝트 행동 코드 실행과 MCP의 임의 호스트 코드/shell 실행은 구분합니다.

M5는 static/kinematic/trigger를 기본으로 하고 동적 rigid body 필요성은 실험에서 결정합니다.
물리 backend와 자산 포맷을 GUI 타입에 결합하지 않습니다. 지원 shape/body·단위·오차와 호출 순서를 문서화합니다.
타일맵·애니메이션·HUD·audio도 같은 문서/명령/runtime 경계에 추가하고 각 단계의 범위 이상으로 일반화하지 않습니다.

## M7 픽셀 작업과 대화형 에셋의 경계

채팅 UI는 문맥/요청을 보여주고 agent/backend가 한정된 작업을 조율하며,
bitmap provider는 생성/수정 후보를 반환합니다. 채팅 모델 자체를 이미지 생성기로 가정하지 않습니다.
픽셀 캔버스의 도구는 GUI·CLI/MCP가 공유하는 픽셀 작업 세션의 명령·검증·stroke 이력을 사용합니다.
이 작업의 draft/후보와 프로젝트의 현재 승인 자산을 분리하고, 승인 전에는 scene/runtime의 그림을 바꾸지 않습니다.

provider 출력 원본을 보존하고 규격 검사·명시적 정규화·preview·비교/보정 뒤에만 새 불변 자산 버전을 적용합니다.
선택 영역 밖은 기준 이미지 픽셀을 합성해 보존합니다. 적용은 예상 자산 버전과 참조 영향을 검증하는 명령입니다.
개체·tileset·후속 frame 참조와 cache를 함께 갱신하고 undo는 기존 버전으로 돌아가며 provider를 다시 호출하지 않습니다.
픽셀 작업의 undo/저장과 프로젝트 적용의 undo/저장 대상을 구분합니다.

job의 기준 참조·버전, provider/model/job, 변형과 승인 근거를 기록하되 권리를 자동 확정하지 않습니다.
늦거나 취소 불명인 결과와 stale 후보가 현재 자산을 자동 덮지 않게 합니다.
키는 OS 보안 저장소 등 외부 사용자 설정으로 관리하고 프로젝트·Git·로그·export에 넣지 않습니다.
provider 미연결에도 수동 도구는 동작하고, player는 승인된 로컬 자산만으로 실행합니다.

## 형식·자산·복구

제품 v1과 프로젝트 `schema_version`은 서로 다른 버전입니다.
첫 새 형식부터 이전 fixture 읽기/migration·미지원 미래 버전 거부·실패 시 원본 보존을 검증합니다.
기존 ID와 상대 자산 참조를 유지하고, 재가져오기·대소문자·한글/공백·누락 파일과 캐시 무효화를 검사합니다.
GPU 자료·디코드 캐시·실행 변수는 편집 문서에 저장하지 않습니다.

저장은 같은 디렉터리의 임시 파일 기록 후 교체하고 실패 시 기존 파일·저장 지점을 보존합니다.
복구 checkpoint는 정상 저장과 분리하고 복원 시점을 표시합니다. 복구가 마지막 정상 저장본을 조용히 덮지 않게 합니다.
최근 복구 지점과 마지막 입력까지 무손실이라는 보장은 구분하며, 새 데이터가 도입될 때부터 복구 범위도 확장합니다.

## player와 export

M3의 최소 독립 player로 프로젝트 로딩과 양 OS 실행 가능성을 일찍 확인하고 M10에서 정식 패키징으로 발전시킵니다.
받는 쪽 게임은 editor·편집용 CLI/MCP 서버·개발 캐시·Rust를 요구하지 않아야 합니다.
일반 배포 runtime에 개발 제어/디버그 capability가 자동 노출되지 않는지도 검증합니다.

지원 CPU·최소 OS·빌드 호스트 후보는 M3 실험에서 고르고 M10 실기기 검증으로 확정합니다.
export 호스트에 필요한 도구와 받는 쪽 게임의 사전 설치 의존성을 구분합니다.
OS별 빌드가 필요할 수 있으며 내부 smoke/ad-hoc 실행과 외부 배포의 서명·공증·채널 검증을 구분합니다.
리소스·행동 코드·폰트·audio의 패키지 포함/사용 조건과 상대 경로를 확인합니다.
